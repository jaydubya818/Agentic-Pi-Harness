- [ ] 2026-08-26 — `docs/HOOK-SECURITY.md` specifies a hook trust model with no enforcement site — the doc was made honest this run (see Closed), which turns the gap into a decision rather than a surprise. The gap itself: nothing reads a hook's `type`, no hook API carries the loop mode (`HookContext`, `PreToolHookContext`, and `PostToolHookContext` all lack a `mode` field), there is no plugin manifest and no signature check, and `makeShellHook` returns an `InProcessHook`, so a shell hook is indistinguishable from a module hook everywhere downstream. Every `✗` in the trust-tier table is therefore a `✓` in practice. Not urgent for the same reason the `write_file` item below is not: none of `HookDispatcher`, `makeShellHook`, or `dispatchPreToolHooks` is exported from `src/index.ts`, which publishes only the Hermes and orchestration surfaces, so no published consumer can register a hook at all. This is the same shape as the "bridge accepts security constraints it silently drops" item below — a validated, accepted, entirely inert control — and it wants the same first step: carry `hookType` and the loop mode on the registration so the gate has somewhere to live, rather than bolting a mode check onto each dispatcher. Note that `HookAuditRecord.hookType` is currently hardcoded to `"module"` at both `dispatcher.ts` call sites, so wiring the audit sink before fixing that would write a false trust-tier claim into the artifact.

There are five such lists, each enumerating a subset of the fifteen classes independently — the `if` chain in `assertKnowledgeWriteAllowed`, `PROMOTION_SOURCE_CLASSES`, `PROMOTION_TARGET_CLASSES`, `GOVERNED_DELETE_DENIED_CLASSES`, and a sixth copy in `preflightV2KnowledgePolicy` over in `httpBridge.ts`.
