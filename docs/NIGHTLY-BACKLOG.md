- [ ] 2026-08-29 — `WorkerModeControls.allowExclusiveTools` is a security control that is inert unless the caller also wires a tool manifest — `evaluateWorkerToolUse` denies an exclusive-class tool with `manifestInfluence: workerControl:exclusiveDenied`, but it does not classify anything itself: it branches on a `toolClass` its caller computes. The only caller is `prepareToolDispatch` (`src/loop/query.ts`), which does `resolveConcurrencyClassifier(inp.concurrency) ?? new ConcurrencyClassifier([])`, and `ConcurrencyClassifier.classify` returns `"serial"` for every name not in its manifest. So when `LoopInputs.concurrency` is absent — which it is on every path in this repo except `tests/unit/queryLoopWorkerControls.test.ts` — **no tool is ever `exclusive`, and the check can never fire.** Reproduced end to end through `runQueryLoop`, not just at the unit boundary: one worker session (`mode: "worker"`, `workerControls: { signedPolicy: true, allowExclusiveTools: false }`) running a `deploy` tool against `{ path: "/etc/shadow" }` comes back `policy.approve: 1` with the tool body executed when `concurrency` is omitted, and `policy.deny: 1` / `tool.denied: 1` with the tool never entered when the same session passes `new ConcurrencyClassifier([{ name: "deploy", class: "exclusive" }])`. No error, no warning, no counter distinguishes the two. This is the third member of the family the 2026-08-24 (V2 envelope `constraints`) and 2026-08-28 (`allowSubagents` / `maxSubagents`) entries opened — a validated, accepted, entirely inert control — but it is the worst of the three, because the other two have *no* enforcement path at all whereas this one has a real, tested enforcement path that silently does not run, and because `docs/EXECUTION-MODES.md` listed it under the three controls it certifies as "Real" (that document is corrected on `main` as of 2026-08-29). Deliberately **not** patched: every available fix is a contract decision rather than a repair. Requiring `concurrency` in `validateWorkerModeInputs` changes the `LoopInputs` contract and breaks the 13 worker-mode cases in `tests/unit/workerControls.test.ts` that legitimately never cared about exclusive tools; defaulting unclassified tools to `exclusive` in worker mode inverts `ConcurrencyClassifier`'s documented default and would deny every unregistered tool; and throwing only on an *explicit* `allowExclusiveTools: false` is incoherent, because `undefined` already means "deny exclusive" everywhere a classifier exists. What is actually needed is one recorded answer to "what is an unclassified tool in worker mode?" — and, whichever way it goes, a signal at session start rather than silence.

- 2026-08-24 — Applying `.strict()` to the rest of the zod surface — the policy fix above raised the obvious follow-up, and the answer is no, not as a sweep. `.strict()` was previously used nowhere in `src`, so turning it on everywhere would change the accept/reject behaviour of every persisted-artifact reader at once, including replay of tapes written by older versions.
